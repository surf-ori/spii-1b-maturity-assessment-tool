# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A self-assessment tool for Open Science infrastructures, currently offering six assessment frameworks: the [Principles of Open Scholarly Infrastructure (POSI) v2.0](https://openscholarlyinfrastructure.org/), a draft SPII v0.0.1 framework, a draft OSR v0.1 framework adapting Jeroen Bosman and Jeroen Sondervan's [open science resilience model](https://upstream.force11.org/the-resilience-of-open-science-in-times-of-crisis/) (related to the International Science Council's *Protecting Science in Times of Crisis*, 2024), a draft framework adapting the [Barcelona Declaration on Open Research Information](https://www.barcelona-declaration.org) (2024), a draft framework adapting the Research Data Alliance's [Global Open Research Commons (GORC) International Model, version 1.1](https://doi.org/10.15497/RDA00119) (2024), and a draft framework transcribing the [FAIR Guiding Principles](https://www.gofair.foundation/fair-principles) (Wilkinson et al., 2016). The app itself is a single standalone `index.html` file — there is no build step, package manager, or committed test suite — but the built-in frameworks live as data in `data/frameworks/*.json` (one file per framework, for manual editing without touching `index.html`) and are loaded into the page at runtime via `fetch()`; see **Running / previewing** for what that means for how the page can be opened, and **Data model** for the loader. Styling comes from the [Oat](https://oat.ink) CSS framework (vendored locally as `oat.min.css`) layered with color/font tokens hand-copied from the [SURF Design System](https://surfnet.github.io/DesignSystem/). The repo lives at [github.com/surf-ori/spii-1b-maturity-assessment-tool](https://github.com/surf-ori/spii-1b-maturity-assessment-tool) (originally a personal account, then [surf-ori/open-science-maturity](https://github.com/surf-ori/open-science-maturity), copied into this repo, SPII deliverable 1B's own tracker, on 2026-09-16 — update any stray references to either older location if you find one). `examples/` holds example POSI assessment reports (JSON) built from real published self-assessments (OpenAIRE, OpenAlex, HAL+/CCSD), linked from the About dialog.

## Running / previewing

Serve the directory with any static file server (for example `python3 -m http.server`) and open `index.html` over http(s) — there is nothing to install or build beyond that. **Opening `index.html` directly as a `file://` page no longer works**: since the built-in frameworks are fetched at startup from `data/frameworks/*.json` (see **Data model**), and browsers block `fetch()` of local files from a `file://` origin (CORS), the page shows a clear on-page error (`render_boot_error`) instead of rendering instead of silently failing. This is a step down from the tool's earlier zero-server "just open the file" story — worth knowing if you're used to that. Also live at https://surf-ori.github.io/spii-1b-maturity-assessment-tool/ via GitHub Pages (legacy build, serving `main` branch root — no workflow file, no separate deploy step; a push to `main` is a deploy), which works fine since GitHub Pages already serves over https. The `?report=`/`?framework=` URL-param loader (see below) needs the same http(s) form for the same reason.

## Architecture

Everything lives in `index.html`: markup, inline `<style>`, and inline `<script>`. There is no JS framework — all rendering and interactivity is vanilla DOM manipulation, driven by a single in-memory `state` object.

**Data model** (`<script id="app-logic">` in `<head>`): `FRAMEWORKS` is the list of *built-in* assessment frameworks, each with a `title`/`description`/`aboutHtml`, optional `draft` flag, and a `sections` array — but unlike earlier versions of this tool, the built-in frameworks are no longer hardcoded as JS constants in `index.html`. `FRAMEWORKS` starts as `let FRAMEWORKS = [];` and is populated at startup by `load_builtin_frameworks()`, an `async function` that `fetch()`es each path in `BUILTIN_FRAMEWORK_FILES` (`["data/frameworks/posi.json", "data/frameworks/spii.json", "data/frameworks/osr.json", "data/frameworks/bd.json", "data/frameworks/gorc.json", "data/frameworks/fair.json"]`, in that order — array order becomes `FRAMEWORKS` order, so `FRAMEWORKS[0]` is still POSI, etc.), parses each as JSON, and runs each through `validate_framework_shape` (throwing with the offending file's path if any fetch, parse, or shape check fails). Each `data/frameworks/*.json` file is a complete framework object — `{id, title, shortName, description, aboutHtml, draft?, sections}` — matching exactly what used to be a `FRAMEWORKS` array entry in JS, just as standalone JSON instead; this is the file to hand-edit when tweaking a built-in framework's principles, criteria, or copy, no `index.html` change required. The six entries: POSI v2.0 (`id: "posi"`, `draft` unset, 3 sections — Governance, Sustainability, Insurance — 20 principles total; `data/frameworks/posi.json`), SPII v0.0.1 (`id: "spii"`, `draft: true`, 5 sections — Openness, Autonomy, Sustainability, Interoperability, Researcher-centric — 19 principles total; `data/frameworks/spii.json`), OSR v0.1 (`id: "osr"`, `draft: true`, 5 sections — Funding, Infrastructure, Academic Freedom, Safety & Wellbeing, Disinformation & Trust Resilience — 25 principles total, five per section, one per resilience type (prevention/protection/resistance/withstanding/repair); `data/frameworks/osr.json`; adapted from Jeroen Bosman and Jeroen Sondervan's open science resilience model, see Notes below), BD Assessment v1.0 (`id: "bd"`, `draft: true`, 4 sections — one per commitment of the [Barcelona Declaration on Open Research Information](https://www.barcelona-declaration.org) (2024) — 8 principles total, two per section, one per sub-commitment; `data/frameworks/bd.json`; see Notes below), GORC v1.1 Assessment (`id: "gorc"`, `draft: true`, 10 sections — one per essential element of the [GORC International Model v1.1](https://doi.org/10.15497/RDA00119) (Governance & Leadership, Rules of Participation & Access, Sustainability, Engagement, Human Capacity, Interoperability, Standards & Conventions, ICT Infrastructure, Services & Tools, Research Objects) — 55 principles total, one per model category plus a handful for Core, element-wide attributes not captured under any single category; `data/frameworks/gorc.json`; by far this tool's largest framework, see Notes below), and the FAIR Principles Assessment (`id: "fair"`, `draft: true`, 4 sections — Findable, Accessible, Interoperable, Reusable — 15 principles total, one per FAIR sub-principle (F1–F4, A1/A1.1/A1.2/A2, I1–I3, R1/R1.1–R1.3); `data/frameworks/fair.json`; see Notes below). Each principle has a stable `id`, `title`, verbatim `text` (transcribed from openscholarlyinfrastructure.org for POSI, from the Declaration's own commitment bullets for `bd`, from the GO FAIR Foundation's published wording for `fair`; `gorc`'s `text` is a close paraphrase of each category's own description and attributes rather than verbatim, since compressing ~290 raw model items down to 55 principles required condensing multiple attributes into one principle's text — see Notes), and may optionally carry `criteria` (an object with `{compliant, progress, "non-compliant"}` keys holding short rubric text shown per status card) and `improvementAction` (text shown as a "To improve:" note) — absent for POSI, present on every SPII, OSR, `bd`, `gorc`, and `fair` principle, rendered only when present so a framework can opt into richer guidance without affecting others. `<script id="app-render">`'s `boot()` (the very last thing the script does — see **Loading from URL parameters** below) awaits `load_builtin_frameworks()`, assigns its result to `FRAMEWORKS`, sets `activeFrameworkId = FRAMEWORKS[0].id`, builds `state = initial_state()`, and only then calls `render()`; a failure at the fetch step calls `render_boot_error(err)` instead, which replaces `#app`'s contents with a plain-language explanation (this is the `file://` failure mode described under **Running / previewing**) and returns without rendering. Because of this, `state`/`activeFrameworkId` both start as `let state = null;`/`let activeFrameworkId = null;` at module scope rather than being initialized inline the way they used to — nothing else in the script reads them before `boot()` sets them, since every other code path only runs from a rendered page or a user interaction, both of which postdate `boot()` completing. Beyond the built-ins, `state.customFrameworks` holds framework objects a user has imported at runtime (same shape as `FRAMEWORKS` entries, and as one `data/frameworks/*.json` file); `<script id="app-render">`'s `all_frameworks()` (`FRAMEWORKS.concat(state.customFrameworks)`) is what rendering code iterates wherever custom frameworks should show up (tabs, sidebar nav, summaries, badge) — a handful of call sites that intentionally still use bare `FRAMEWORKS` (the `initial_state()` build, the default `activeFrameworkId`, and `merge_loaded_state`'s id-collision check) stay built-ins-only on purpose. `validate_framework_shape(obj)` is the shared structural check (id/title/sections[].section/sections[].principles[].id·title·text) used when importing a framework at runtime, when reloading a previously-exported report that included `customFrameworks`, and now also by `load_builtin_frameworks()` on every fetched built-in; `framework_state_slice(framework)` builds the `{principleId: {status: null, notes: ""}}` slice for a framework, shared by `initial_state()` and by custom-framework import/reload. `ACTIVITIES` is `{primary, related}` — two named, boxed groups for the "Classify" picker ("Research life cycle activities" and "Research related activities"), 12 items total. `ICONS` holds the three inline SVG status icons; `ACTIVITY_ICONS` holds one inline SVG per classification item (keyed by the item's exact label), rendered via the shared `activity_icon_markup(item, size, strokeColor, extraAttrs)` helper — next to each Classify checkbox (`currentColor`, tinted via the `.activity-icon` CSS class) and, for whichever items are selected, as a row of small icons in the assessment badge (`#333333`, positioned with explicit `x`/`y` since that markup is a standalone exported SVG with no CSS context). `initial_state()` builds a fresh `state` object: `{name, description, url, assessedOn, activities, customFrameworks, frameworks: {[frameworkId]: {[principleId]: {status, notes}}}}`, where `status` is `"compliant"`, `"progress"`, `"non-compliant"`, or `null`, and `assessedOn` defaults to today's date (`today_iso_date()`). `compute_summary(state, frameworkId)`, `build_export_object(state)`, `merge_loaded_state(loaded)`, `validate_framework_shape(obj)`, `framework_state_slice(framework)`, and `ring_segment_offsets(radius, count)` are pure functions with no DOM access — this is what makes them testable outside a browser (see Testing below).

**Rendering** (`<script id="app-render">` in `<body>`): `render()` rebuilds `#app` entirely from the global `state` — the header (just the intro paragraph now — see **About/Changelog dialogs** below for where that content lives) and `render_tabs()`, which wraps everything else in a hand-rolled tab strip: one tab for "OS Infrastructure Description" (name/description/URL/assessment-date fields, plus "Classify" as a sub-heading with two boxed activity columns using Oat's `.row`/`.col-6` grid) and one tab per `all_frameworks()` entry (title, optional draft `role="alert"` banner, description, "About `<framework>`" accordion, framework-level summary with scoped id `summary-heading-<frameworkId>`, each content sub-section's DOM id generated by `section_id(frameworkId, section)` — a slugified section name scoped to its owning framework, not hardcoded, so id collisions can't occur even if two frameworks reuse a section name — then one `<details id="principle-<frameworkId>-<principleId>" data-principle-id="..." data-framework-id="<frameworkId>">` per principle — 3 status cards with icons + a notes `<textarea>`). Tabs use plain `role="tablist"`/`role="tab"`/`role="tabpanel"` markup (styled by `oat.min.css`, which ships the CSS for Oat's `<ot-tabs>` pattern but not its JS) with `switch_tab(tabId)` handling the `aria-selected`/`hidden` toggling by hand — there's no new dependency, and no `<ot-tabs>` custom element to register. `activeTabId`/`activeFrameworkId` are both module-level (not persisted in exported JSON); switching to a framework's tab also sets `activeFrameworkId` and calls `update_badge()`, so the assessment badge always reflects whichever framework tab was last viewed. `navigate_to(tabId, anchorId)` is the single place that switches tabs, force-opens a `<details>` target, and scrolls to it — used by every sidebar nav link (framework, section, and per-principle). `render_sidebar_nav()` now goes one level deeper than framework → section: each section also lists its principles individually via `render_principle_nav_link`, each prefixed with a `.nav-status-icon` — the same `ICONS[status]` markup the status cards use (plus a 4th `ICONS.unanswered`, a bare circle, for `null`) — colored via `[data-status]`; `update_principle_status_icon(frameworkId, principleId, status)` — called from `set_status()` — swaps the icon's `innerHTML` and `dataset.status` in place without a full re-render. A plain colored dot was tried first but flattened into an oval whenever its principle's title wrapped to multiple lines, since the containing `<a>` is a flex row and flexbox's default `align-items: stretch` stretches a fixed-height flex item to match a taller sibling; `.nav-status-icon` fixes this the same way regardless of icon-vs-dot (`align-self: center` + `flex-shrink: 0`), and reusing the status-card icon set was also just a better fit visually than a separate dot vocabulary. A framework's nav group defaults open when `!framework.draft` and collapsed when `draft: true`. The sidebar footer (`render_sidebar_footer`: the assessment badge + hovercard, and the badge SVG/PNG/embed export buttons, all inside a `<details>` accordion — see **Styling** for why it's collapsed by default and opens upward) is rebuilt on every `render()` too; the page's title, mobile nav toggle, and Import/Export menus live in a static `nav[data-topnav]` in the body (never rebuilt by `render()` — its buttons are wired once, at the bottom of the script, alongside the other delegated listeners). Interaction handlers (`set_status`, `toggle_activity`, the notes/field input listeners) mutate `state` directly and call the narrower `update_summary()` (which also refreshes each tab's live "(scored/total)" label via `tab_label_text`) /`update_badge()` rather than a full `render()`, so typing in a field doesn't lose focus. `render()` itself is called on first load, after a JSON report is loaded (`load_json`), and after a custom framework is successfully imported (`import_custom_frameworks`), since those are the only times the whole DOM tree needs rebuilding from a new `state`.

**When adding a new POSI principle**: add it to the relevant section's `principles` array in `data/frameworks/posi.json` — the UI, scoring, JSON export/reload, and badge all render from that data automatically once fetched. Same pattern for SPII (`data/frameworks/spii.json`), OSR (`data/frameworks/osr.json`), BD Assessment v1.0 (`data/frameworks/bd.json`), GORC v1.1 Assessment (`data/frameworks/gorc.json`), and the FAIR Principles Assessment (`data/frameworks/fair.json`). **When adding a new activity**: add it to the `ACTIVITIES` data in `<script id="app-logic">` (this one is still inline JS, not fetched — see Notes for why activities and frameworks aren't handled the same way). Don't hand-edit the generated `<details>` markup; it's rebuilt by `render()` on every load.

**Top bar** (`nav[data-topnav]`, static markup in `<body>`, never rebuilt): the mobile sidebar toggle, the SURF logo (inline `<svg>`, fetched once from surf.nl and embedded verbatim — `aria-hidden="true"` since the adjacent title text already carries the accessible name), the app title, and two menus built from Oat's `<ot-dropdown>` pattern (a plain wrapper tag — no custom-element JS — around a `popovertarget` button and a native `[popover]` panel; `oat.min.css` styles both scoped under `ot-dropdown`). Native popovers have no built-in anchoring to their trigger, so `position_popover(button, popover)` sets the popover's `left`/`top` from the button's `getBoundingClientRect()` on its `toggle` event (`newState === "open"`), with a right-edge clamp so the Export menu doesn't overflow off-screen on narrow viewports; a delegated click listener on each popover closes it (`hidePopover()`) after any `[role="menuitem"]` click, since popovers don't auto-close on an interior click. **Import**: "Import Assessment Report (JSON)" (`load_json`, via a hidden file input), "Import Assessment Framework (JSON)" (`load_custom_frameworks` → `import_custom_frameworks`, same file-input pattern), "Download Assessment Framework Template (JSON)" (`download_framework_template`, downloads the static `FRAMEWORK_TEMPLATE` object as a starting point for authoring a custom framework). **Export**: "Export Assessment Report (JSON)" (`download_json`), "Print Assessment Report (PDF)" (`download_pdf`), "Download Assessment Frameworks (JSON)" (`download_all_frameworks`, exports `all_frameworks()` — built-ins and any imported customs together, so the file is self-contained) — all three, like every Import item, carry a `.menuitem-desc` one-liner. Two more plain (`.ghost`) buttons, "About" and "Changelog", sit after the Export menu — see below. `oat.min.css` declares its own `[role=menuitem]` rules — including the `:hover`/`:focus` highlight — inside `@layer components`; CSS cascade layers make ANY unlayered author style win over ANY layered one regardless of selector specificity, so this file's own unlayered `[role="menuitem"] { background-color: transparent; ... }` override (needed so menu items don't inherit the solid-primary base `button` look) was silently eating Oat's hover highlight too. Fixed by restating `[role="menuitem"]:hover,:focus { background-color: var(--accent); }` here as well — worth remembering for any future override of an Oat component rule, not just this one.

**Error/warning notices**: `show_toast(message, variant)` (`<script id="app-render">`) is how the app now surfaces transient errors and warnings — a JSON-import failure, a partial custom-framework import, a failed `?report=`/`?framework=` fetch, a failed badge-image render — instead of a blocking `window.alert()`. It appends a `[role="alert"][data-variant="error"|"warning"]` element (reusing the same Oat-styled pattern as a framework's `draft: true` banner and `render_boot_error`, not a new visual language) with a close button to the static `#toast-region` (a sibling of `#app-shell`, never rebuilt by `render()`), and auto-removes it after 8 seconds; `aria-live="assertive"` on the container means screen readers announce it as it's added. `#toast-region` is `position: fixed` with `top: 5rem` hardcoded to clear `nav[data-topnav]`'s rendered height (it's `position: sticky` from Oat and sits at the very top of the viewport) — if the top bar's height ever changes, this offset needs to move with it.

**About/Changelog dialogs**: `<dialog id="about-dialog">`/`<dialog id="changelog-dialog">` are static markup in `<body>` (siblings of the topnav, never rebuilt), opened by their topnav trigger buttons via the native declarative Invoker Commands API (`commandfor="about-dialog" command="show-modal"` on the opener, `command="close"` on the in-dialog Close button — no click-handler JS needed for open/close) and `closedby="any"` (click-outside or Escape also closes them). This is a very new browser API; there's no JS fallback wired for browsers that don't yet support it. `ABOUT_TOOL_HTML`/`CHANGELOG_HTML` (unchanged data-side) are injected into `#about-dialog-content`/`#changelog-dialog-content` once, in the one-time listener setup at the bottom of the script — `render()` never touches them, since their content doesn't depend on `state`. `oat.min.css` already styles bare `<dialog>` (centered, backdrop, `header`/`form>footer` padding) — the `<form method="dialog">` wrapper and `header`/`div`/`footer` structure follows Oat's own documented dialog pattern exactly. Oat's own dialog CSS already puts `overflow-y: auto` on the content div (`:is(&,&>form)>:is(p,div,section)`), but neither `<dialog>` nor its `<form>` was a flex container, so that div's height was just its content's natural size — nothing ever constrained it smaller, so the `overflow-y: auto` never actually triggered a scrollbar, and content past `<dialog>`'s own `max-height: 85vh` (also Oat's) was simply clipped with no way to reach it, on both dialogs, once their content grew past one viewport. Fixed by this file's own `dialog[open] { display: flex; flex-direction: column; }` plus the same on `dialog > form`, letting `#about-dialog-content`/`#changelog-dialog-content` (`flex: 1; min-height: 0`) actually shrink within that now-bounded column so Oat's `overflow-y: auto` has something to do. The `[open]` in `dialog[open]` is load-bearing: the browser's own UA stylesheet sets `dialog:not([open]) { display: none }`, and a bare `dialog { display: flex }` overrides that default even while closed — Oat's closed-state styling (`opacity: 0`, `transform: scale(.95)`) only fades it out, it doesn't hide it via `display`, so an unscoped rule here left both dialogs sitting in the layout — full-viewport (`position: fixed; inset: 0` per Oat), invisible, and still catching every click on the page underneath them — any time neither dialog had ever been opened. This shipped once, briefly, before a Playwright click failure ("`dialog#changelog-dialog` subtree intercepts pointer events" on an unrelated button, on a page where neither dialog had been opened at all) caught it — worth remembering because a screenshot alone won't show it; the dialog really is invisible right up until something tries to click through where it's sitting.

**Custom framework import**: `add_valid_frameworks(frameworks)` is the shared mutation — for each entry, checks `validate_framework_shape` and every existing framework id (built-in and already-imported) via `all_frameworks()`, then adds valid/non-colliding ones to `state.customFrameworks` plus a fresh `state.frameworks[id]` slice via `framework_state_slice`, returning `{addedCount, skipped}`. `import_custom_frameworks(frameworks)` (the top-bar "Import Assessment Framework" flow, and re-importing a "Download Assessment Frameworks" export) wraps it with a `render()` if anything was added and an `alert()` listing anything skipped. `build_export_object`/`merge_loaded_state` round-trip `state.customFrameworks` (plus their scores) the same way they already round-trip the built-ins, so a custom framework you're partway through scoring survives an Export/Import Assessment Report cycle. `merge_loaded_state(loaded, base)`'s second argument is optional (defaults to a fresh `initial_state()`) — passing an already-populated state as `base` layers `loaded` on top of it instead of starting over, which is what lets `load_from_url_params()` (below) combine a `?framework=` load with a `?report=` load without losing the framework or double-adding it; its `customFrameworks` dedup is seeded from `base.customFrameworks` as well as the built-ins, not just the built-ins, for the same reason.

**Loading from URL parameters**: `load_from_url_params()` (called once, after the initial `render()`, at the very bottom of the script) reads `?framework=<url>` and/or `?report=<url>` from `window.location.search` and `fetch()`s each as JSON (`fetch_json_url`, which `alert()`s and resolves to `null` on any HTTP or parse failure rather than throwing). If a framework loaded, `add_valid_frameworks` adds it (the fetched JSON may be a single framework object or an array of them, same as a file-based import); if a report loaded, `merge_loaded_state(reportData, state)` layers it onto whatever state exists at that point (so a framework loaded via the other param, if any, is already present and gets scored rather than clobbered) — then `render()` runs once at the end if anything changed. Because this uses `fetch()`, it only works when the page is served over http(s); opening `index.html` directly via `file://` will have these requests blocked by the browser, same as any other cross-file fetch from a `file://` page.

**Export flows**:
- `download_json_blob(data, filename)` is the shared JSON-blob-download helper (`JSON.stringify` → `Blob` → `trigger_download`); `download_json()`, `download_framework_template()`, and `download_all_frameworks()` are all thin wrappers over it.
- `download_pdf()` renders `document.body` via `jsPDF` (loaded from a CDN, `doc.html()`) into `report.pdf`. Because `doc.html()` renders via html2canvas using the page's on-screen computed styles, it does not fire `beforeprint`/honor `@media print`, so `download_pdf()` does its own force-open of every `<details>`, temporarily un-hides every `[role="tabpanel"]` (so all frameworks' content is captured regardless of which tab was active), and toggles a plain `body.printing` class (mirrored by a non-media-query CSS rule) to hide the top bar, the sidebar footer's buttons, and unselected status cards — restoring the original `<details>` open/closed and tabpanel `hidden` state once the PDF is saved. The browser's own print preview (Ctrl/Cmd+P) instead uses the `@media print` rules directly, with `beforeprint`/`afterprint` listeners doing the same force-open/un-hide-tabpanels/restore dance.
- `build_badge_svg_markup(state)` builds a self-contained `<svg>` (using the title from the active framework, concentric rings computed via `ring_config_for(framework)` — one per section, each split into one arc per principle via `ring_segment_offsets` — the overall `%`, infrastructure name, a row of the selected activities' icons via `selected_activity_items(state)` + `activity_icon_markup`, and the assessment date) — deliberately compact; the full per-section breakdown lives in `build_badge_hovercard_html(state)`, shown as a `.hovercard` on hover/focus of the badge (plain CSS, no new dependency). `download_badge_svg()`/`download_badge_png()` export the compact badge as a static image the infrastructure can host on its own site. `build_badge_embed_html(state)` builds a third option — a fully self-contained `<div>` (inline `<style>`, plain hex colors rather than this app's own CSS custom properties, since a page it's pasted into won't have those tokens defined) combining `build_badge_svg_markup` and `build_badge_hovercard_html` plus the same hover/focus-reveal interaction as the in-app `.hovercard`, scoped under an `.osmat-badge-embed` class to avoid colliding with the host page's own styles. `copy_badge_embed()` (wired to the sidebar's "Embed badge" button) copies that string to the clipboard via the async Clipboard API and confirms with `show_toast(..., "success")`; if `navigator.clipboard`/`window.isSecureContext` isn't available, or the write itself rejects, it falls back to `download_badge_embed()` (downloads `badge-embed.html`) with a `"warning"` toast explaining why. This is a snapshot of `state` at the moment "Embed badge" is clicked, not a live/dynamic embed — there's no backend for a pasted snippet to call back into, so a static, self-contained copy is the only kind of embed this tool can offer.

**Styling**: color and font tokens are hand-copied from the [SURF Design System](https://surfnet.github.io/DesignSystem/) as CSS custom properties (`--primary`, `--warning`, `--destructive`, `--compliant`, `--font-sans`) in `:root`, with dark-mode overrides under `@media (prefers-color-scheme: dark)`. This is a copy of token *values*, not a dependency on SURF's packages — the page has no new runtime dependency beyond the pre-existing jsPDF/html2canvas CDN scripts, plus the Google Fonts stylesheet below. `--font-sans` names `"Source Sans 3"`, but nothing actually loaded that font until a `<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Source+Sans+3:...">` was added to `<head>` (with a matching `preconnect`) — before that, every browser was silently falling back to `sans-serif` on every declaration that referenced the token, including the three `font-family="&quot;Source Sans 3&quot;, sans-serif"` attributes baked into the exported badge SVG's `<text>` elements. Beyond those tokens, layout and typography lean on Oat's own system rather than reimplementing it: the custom `<style>` block only overrides what Oat doesn't already provide, and otherwise sizes/spaces things with Oat's own `--text-N`/`--space-N` custom properties and its `.row`/`.col-N` grid (status cards, the Classify columns, and the URL/date field pair all use `.row` + `.card`/`col-N` rather than ad-hoc flexbox, so they get Oat's built-in mobile stacking at 768px for free). `#app` is capped at `var(--container-max)` and centered so content doesn't stretch edge-to-edge on wide screens. `[role="tabpanel"]` gets a `.card`-like background/border/padding/`box-shadow: var(--shadow-small)` so each tab reads as a distinct boxed panel, matching what Oat's own `.card` class gets; `[role="tab"]`/`[role="tablist"]` rely entirely on Oat's own styling. `.status-card` (the compliant/progress/non-compliant picker, `role="button"`) gets its own hover (`background-color: var(--accent)`) and active (`transform: scale(0.98)`) states — it's a plain `<article>`, not a `<button>`, so it doesn't inherit Oat's `button:hover` rule the way the topnav's actual `<button>`s do. `h1`–`h4`/`.summary-heading` get `text-wrap: balance` and `p` gets `text-wrap: pretty`, both no-op in browsers that don't support them yet. `.nav-status-icon[data-status]` colors the per-principle sidebar icons from the same `--compliant`/`--warning`/`--destructive` tokens the status cards use, defaulting to `--border` (grey) when unanswered. `--sidebar-width` is bumped from Oat's default `15rem` to `18rem`; the sidebar nav itself otherwise keeps Oat's own (deliberately compact) font size and link padding as-is. `[role="menuitem"]` resets the background/border/color that `oat.min.css` doesn't itself clear for menu items rendered as `<button>` (they'd otherwise inherit the solid-primary base `button` styling and look like stacked buttons rather than menu rows). Fixing the topnav's mobile overflow (found via real-device screenshots, not the dev-container's own viewport-emulated testing — see below) took three layered fixes, all real bugs rather than one: (1) `nav[data-topnav]` itself is `grid-column: 1 / -1` inside `#app-shell`'s grid, and — exactly like a flex item — a grid item's default `min-width` is `auto` (its content's own min-content size), not `0`; that let nav's rendered box grow wider than its `1fr` track to fit its buttons' natural width instead of shrinking to the viewport, so `nav[data-topnav]` now also sets `min-width: 0`. (2) Even shrunk to the viewport's width, the Import/Export dropdowns plus the About and Changelog buttons alone need roughly 340px, which doesn't fit next to the logo on a ~360-412px phone regardless of what the title does — `nav[data-topnav]` now also sets `flex-wrap: wrap` so they flow onto a second (or third) row instead of forcing nav wider than its grid track. (3) `nav[data-topnav] > strong` (the app title) additionally has `min-width: 0; max-width: 100%; overflow: hidden; white-space: nowrap; text-overflow: ellipsis` so it truncates with an ellipsis on its own row rather than wrapping across the roughly six lines its intrinsic width would otherwise take (both `min-width: 0` — a flex item's default is `auto`, not `0` — and `max-width: 100%` are load-bearing here; `min-width: 0` alone wasn't sufficient once nav could wrap, because an item alone on a wrapped flex line isn't reliably shrunk by `flex-shrink` the way one sharing a line with other items is). `#app-shell > main` (`#app`) needed the same `min-width: 0` fix for the same grid-item reason; `body` additionally has `overflow-x: hidden` as a defensive backstop for the ~10px of residual `min-content` overflow that remains at the narrowest real device width tested (320px, e.g. first-gen iPhone SE) from no single identifiable element — nothing on the page relies on horizontal scrolling, so clipping it is safe. Because nav's height is no longer a fixed constant (72px un-wrapped, up to ~196px wrapped across 3 rows on a 320px phone), `#toast-region`'s CSS `top: 5rem` is now only the pre-JS fallback; `show_toast()` overwrites it with `nav[data-topnav]`'s actual current `getBoundingClientRect().bottom` on every call, since a toast can be triggered at any viewport width. Separately, `[data-sidebar-toggle]` (the mobile hamburger button) explicitly sets `color: var(--foreground)` — `oat.min.css`'s base `button` rule sets `color: var(--primary-foreground)` (white) globally, and `[data-sidebar-toggle]` only overrode `background` (to `none`), not `color`, so the icon inside it — first a Unicode "☰" character, now an inline SVG — has always rendered white-on-white and invisible; this one *looked* like a missing-glyph/tofu-box problem from a phone screenshot alone, and wasn't caught as a color bug until checking the button's computed styles directly. `#sidebar-footer`'s `<details>` (the badge accordion) is `display: flex; flex-direction: column-reverse` — since `aside[data-sidebar]` pins `#sidebar-footer` to the bottom of the sidebar (Oat's own `margin-block-start: auto`), opening it "downward" the way `<details>` normally does would expand into the aside's bottom edge rather than into visible space; `column-reverse` keeps `<summary>` (the first DOM child) anchored at the box's visual bottom and stacks the rest of the accordion's content — `.badge-wrap`, the three export buttons — above it instead, so it reads as unfurling upward. Everything else about its look (border, chevron rotation on `[open]`, hover background, padding) is Oat's own generic `details`/`summary` styling, unmodified; only direction is overridden, plus `details > *:not(summary) { margin: 0 }` replacing Oat's per-child `margin: var(--space-4)` with a flex `gap` instead, so spacing stays even regardless of which child ends up visually first after the reversal.

None of the above was caught by this repo's own Playwright-based dev-container testing before it shipped — real-device screenshots (Android Chrome and Android Firefox) caught it first. The dev-container checks had asserted individual elements' computed sizes and a page-level `document.documentElement.scrollWidth <= clientWidth` check at a few viewport widths, but the specific widths tried happened to land above the ~370px threshold where nav's un-fixed overflow became visible, and the color/contrast bug on the hamburger icon has no automated signal at all (nothing was structurally broken — text and an SVG were both present in the DOM, just invisible). Worth remembering next time: test at multiple real device-preset widths including the narrowest common ones (320px), not just one, and check computed `color`/contrast for icon-only interactive elements, not just their presence in the DOM.

## Testing

There is no committed test suite — this matches the project's "no build step" philosophy. The pure functions in `<script id="app-logic">` (`compute_summary`, `build_export_object`, `merge_loaded_state`, `validate_framework_shape`, `framework_state_slice`, `ring_segment_offsets`) have no DOM dependency and can be exercised from Node by extracting that script block's text (regex on `<script id="app-logic">...</script>`) and running it in a `vm.createContext`, if you need to verify logic changes without a browser — `load_builtin_frameworks()` lives in that same script block but isn't one of these pure functions (it calls `fetch()`), so exercising it from Node either needs a `fetch` stub injected into the `vm` context or is easier to just skip in favor of the manual browser check below. When editing a `data/frameworks/*.json` file directly, `JSON.parse()` it and run it through `validate_framework_shape` (from the extracted `vm` context) as a quick sanity check before reaching for a browser. Everything else (rendering, interactivity, PDF, badge image export, and confirming the built-in frameworks actually load) is verified manually by serving the directory (see **Running / previewing** — plain `file://` no longer works for this) and opening `index.html` in a browser.

## Notes

- A framework's `draft: true` flag (on a `FRAMEWORKS` entry, built-in or custom) renders as a `role="alert" data-variant="warning"` banner (styled by `oat.min.css`) at the top of that framework's tabpanel, and as a "(draft)" suffix in its sidebar navigation link; this allows frameworks to be marked as unfinished individually. POSI has no `draft` field, so it shows no banner; SPII, OSR, `bd`, `gorc`, and `fair` all set `draft: true`, so their banners appear.
- `data/frameworks/*.json` (`posi.json`, `spii.json`, `osr.json`, `bd.json`, `gorc.json`, `fair.json`) hold the built-in frameworks as standalone JSON, one file per framework, meant to be hand-edited directly (see **Data model**). `BUILTIN_FRAMEWORK_FILES` in `index.html` is the ordered list of paths `load_builtin_frameworks()` fetches; adding another built-in framework means dropping a new JSON file in `data/frameworks/` *and* adding its path to that array — there's no directory-listing/manifest indirection, so the array is the single source of truth for which files get loaded. `ACTIVITIES` (the Classify picker's taxonomy) deliberately stayed as an inline JS object in `<script id="app-logic">` rather than moving to `data/`: it's small, framework-independent, and not part of what "framework" means anywhere else in the codebase (`validate_framework_shape`, custom-framework import, `FRAMEWORK_TEMPLATE`), so moving it would have added a fetch with no matching precedent to extend rather than following one.
- OSR (`id: "osr"`) is this tool's own adaptation of the resilience model in Jeroen Bosman and Jeroen Sondervan, *The Resilience of Open Science in Times of Crisis* (Upstream, FORCE11, 13 May 2025, [DOI](https://doi.org/10.54900/pqrcx-8d019)) — not an official assessment instrument published by the original authors, FORCE11, or the International Science Council (whose *Protecting Science in Times of Crisis*, 2024, is a related, independently authored whitepaper the blog post itself references as a parallel multi-phase resilience model). The blog post's own five resilience types (prevention, protection, resistance, withstanding, repair) — applied against five areas of concern (funding, infrastructure, academic freedom, safety, disinformation) — become the 5×5 section/principle structure of the `OSR` constant; its `aboutHtml` spells out this attribution and the "not an official instrument" caveat, so keep both in sync if the OSR content changes.
- BD Assessment v1.0 (`id: "bd"`, `data/frameworks/bd.json`, titled "BD Assessment v1.0" in the UI to keep the tab label short — see the mobile-overflow history under **Styling**) is this tool's own adaptation of the [Barcelona Declaration on Open Research Information](https://www.barcelona-declaration.org) (16 April 2024, [DOI](https://doi.org/10.5281/zenodo.10958522)) — not an official assessment instrument; the Declaration itself has no scoring mechanism. Unlike OSR, the eight principles' `text` is transcribed verbatim from the Declaration's own four commitments and their sub-bullets (the same convention as POSI), since it's a fixed, citable, signed document rather than source material to synthesize a model from; only the `criteria`/`improvementAction` fields (compliant/progress/non-compliant per principle) are this tool's addition, since the Declaration was written for signing organizations broadly (research funders, performers, evaluators) rather than as a rubric for an individual infrastructure to score itself against. The Declaration explicitly names POSI as the kind of good practice signatories should expect from infrastructures they support (principle `bd-expect-good-practice`), which `aboutHtml` and that principle's own text both surface.
- GORC v1.1 Assessment (`id: "gorc"`, `data/frameworks/gorc.json`, titled "GORC v1.1 Assessment" in the UI to keep the tab label short; the full "Global Open Research Commons (GORC) International Model, version 1.1" name lives in `aboutHtml` instead, where there's room for it) is this tool's own adaptation of the Research Data Alliance's [Global Open Research Commons (GORC) International Model, version 1.1](https://doi.org/10.15497/RDA00119) (Woodford et al., 2024, RDA, [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)) — not an official assessment instrument; the model itself is explicitly "aspirational" and "not prescriptive", with no pass/fail scoring mechanism of its own. The source model (published as a spreadsheet, ~290 rows) is far larger and more granular than this tool's other frameworks: ten essential elements (its own spreadsheet tabs, used as this framework's ten sections), each broken into categories and sometimes subcategories, in turn broken into attributes and (for the most complex) features, with every row marked `Core`, `Desirable`, or `Optional`. This tool's `gorc` framework compresses that hierarchy down to one principle per category (52 of them) plus a handful of additional principles for Core, element-wide attributes that sit above any single category in the source (e.g. `gorc-ict-general`, `gorc-st-general`, `gorc-ro-accessibility`) — 55 principles total. Because of that compression, `gorc` principles' `text` is a close paraphrase of the category's own description and its most important attributes rather than a verbatim transcription (contrast `bd`/POSI, which quote their source verbatim); `criteria` are this tool's own operationalisation of the model's Core/Desirable/Optional consideration levels into a compliant/progress/non-compliant rubric — the model itself only says Core items "should be considered by all commons", not that they must be fully implemented to "pass". As the largest and most heavily compressed framework here, expect its principle boundaries and criteria to be revised more than the others. The source model's own KPIs & Metrics sheet and Glossary are not represented in `gorc.json` at all — only the ten essential-element sheets (categories/subcategories/attributes/features) were used.
- The FAIR Principles Assessment (`id: "fair"`, `data/frameworks/fair.json`) is this tool's transcription of the [FAIR Guiding Principles](https://www.gofair.foundation/fair-principles) — Wilkinson, M., Dumontier, M., Aalbersberg, I. et al. "The FAIR Guiding Principles for scientific data management and stewardship." *Sci Data* 3, 160018 (2016), [DOI](https://doi.org/10.1038/sdata.2016.18) — as maintained today by the GO FAIR Foundation. Like POSI/`bd`, the fifteen sub-principles' `text` (F1–F4, A1/A1.1/A1.2/A2, I1–I3, R1/R1.1–R1.3) is transcribed verbatim from the GO FAIR Foundation's own published wording, cross-checked against the machine-actionable [FAIR Vocabulary](https://w3id.org/fair/principles/terms/FAIR) ontology (Tobias Kuhn and Michel Dumontier, CC BY 4.0), whose `FAIR-SubPrinciple` individuals define the same fifteen items and whose top-level `FAIR-Principle` individuals (F, A, I, R) become this framework's four sections. Only `criteria`/`improvementAction` are this tool's own addition, since the FAIR principles themselves describe essential aspects of good stewardship without a pass/fail scoring mechanism of their own — this is one reasonable operationalisation of them for self-assessment, not an official GO FAIR rubric.
- The linked `jspdf` and `html2canvas` scripts are pulled from `unpkg.com` / `html2canvas.hertzen.com` CDNs — there is no local vendoring for these two.
- The app's title now appears exactly once, in the static top bar's `<strong>` — there is no separate sidebar heading or main-content `<h1>` any more.
- The favicon (`<link rel="icon">` in `<head>`) is the same SURF logo SVG as the top bar, base64-embedded as a `data:` URI — self-contained, no separate icon file and no request to surf.nl at runtime.

This repository also doubles as SPII deliverable 1B's feedback and issue tracker (see the
[spii-overview](https://github.com/surf-ori/spii-overview) project). `.github/ISSUE_TEMPLATE/feedback.yml`
collects name, organisation, role, and "representing infrastructure" alongside a feedback issue,
so its origin stays traceable — this is separate from the app code above, and doesn't affect it.

working"](https://surf-ori.github.io/spii-overview/#way-of-working) section on spii-overview for
the full process: a curator triages each issue and records the outcome (accepted, rejected, or
already covered) with a short rationale before closing it. Curators are not yet assigned; until
one is, leave issues open for a human curator rather than closing them on your own judgement.

If an agent drafts a closing comment or decision on an issue here, follow the
`labeling-ai-generated-content` skill: say plainly that it was drafted with AI assistance.
